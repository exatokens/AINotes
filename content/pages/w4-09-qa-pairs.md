Of all the artifacts, the question–answer pair is the most mischievous — and the most direct attack on the costume problem.

The idea is simple: given a chunk, have an LLM generate the plausible questions that chunk could answer, paired with their answers, and embed both.

## Core intuition

When a query and a document are both phrased as questions, the retrieval problem becomes much easier. QA pairs convert declarative content into the same semantic register as natural user requests.

## Why it matters

This is the strongest way to reduce the query-document mismatch. Instead of comparing a question against prose, the system compares a question against question-shaped artifacts that are far closer to the user's actual language.

## Instructor framing

The failure mode at the bottom of this page — a synthetic question whose answer the source doesn't actually support — deserves more classroom time than the generation mechanics. It is the one artifact-generation risk in this week that can actively make the system *worse* than no derivative artifact at all, by confidently retrieving evidence for a claim the source never made. Treat "read the artifacts, not just the metrics" as a mandatory QA step, not an aspirational best practice.

## Worked example



QA pairs are the perfect illustration of the chapter's theme: the retriever needs a representation that speaks the user's dialect, not the author's dialect.

## Why it works

Retrieval is a matching problem, and matching is easiest when both sides speak the same dialect. A dense retriever compares a query embedding with document embeddings. Ordinarily this is a cross-genre comparison — a question measured against declarative prose. But if the indexed object was itself derived from a question, the comparison becomes same-genre: question against question. You have planted a query-shaped decoy that the retriever should find.

## Generating a good set

A good QA pipeline generates three to eight questions per chunk, varied:

- **in specificity** — from "what does this section discuss?" to "what learning rate did experiment 3 use?"
- **in formulation** — keyword-ish to natural-language
- **in abstraction** — factual to interpretive

Each pair stores a pointer back to its source chunk, because at generation time the model must see the chunk, not the synthetic question.

```python
# QA-pair generation, with the pointer that keeps generation honest
def generate_qa_pairs(chunk_id, chunk_text, llm_fn, n=(3, 8)):
    prompt = f"""Generate {n[0]}-{n[1]} question-answer pairs a user might ask
that this passage answers. Vary specificity, phrasing, and abstraction.

Passage:
{chunk_text}"""
    pairs = llm_fn(prompt)  # -> [{"question": ..., "answer": ...}, ...]
    for p in pairs:
        p["source_chunk_id"] = chunk_id   # never sever this pointer
    return pairs
```

## The failure mode to watch for

A careless synthetic question can mislead the retriever, promising an answer the source does not actually contain. Generation hygiene matters: read the artifacts, not just the aggregate metrics. Find the synthetic question whose answer the source does not actually contain — it is invisible in a Recall@k table and obvious on the page.






## Math explained step by step

Formalize "same-genre match" as a claim about where embeddings land, step by step.

**Step 1 — treat genre as a direction, not just a property.** Two texts written in the same genre (both questions, or both formal prose) tend to share syntactic and structural features that pull their embeddings toward a common region of the space, independent of their specific topics — this is the same register effect from the previous page, generalized.

**Step 2 — see why a raw chunk and a user query are genre-mismatched by default.** A chunk is declarative prose; a query is typically an interrogative, elliptical, or keyword-fragment. The comparison $\cos(q, \text{chunk})$ is always fighting this baseline genre gap on top of whatever topical similarity exists.

**Step 3 — see why generating a question from the chunk removes that gap by construction.** A QA pair's question, generated by an LLM instructed to phrase it as "what a user might ask," is drawn from the same genre distribution as real user queries — interrogative, concise, often starting with "what," "how," or "why." Comparing $\cos(q, \text{generated question})$ is now a same-genre comparison: both sides are questions, so only the topical/content difference remains to explain any gap.

**Step 4 — see precisely what this does and does not fix.** It removes genre mismatch, the same mechanism passage rewrites used for register mismatch. It does *not* guarantee the generated question is accurate — a QA pair's power comes entirely from how well its question matches real query genre and how faithfully its (unused-for-citation) answer reflects the source; a well-phrased question paired with an unsupported answer still retrieves correctly but risks the "failure mode to watch for" described above once the pointer leads to a chunk that can't actually back up what was implied.

## Practical pattern

Standing up a QA-pair pipeline:

1. generate 3-8 pairs per chunk with explicit instructions to vary specificity, phrasing, and abstraction — a narrow set of near-identical questions wastes generation budget without covering the real query distribution;
2. always store the source chunk pointer with each pair, and route generation exclusively to the source chunk, never to the QA pair's own answer text — the QA pair's answer exists only to help the LLM generate a good, on-topic question, not to be quoted;
3. audit a sample of generated questions against their source chunks by hand, specifically hunting for questions whose implied answer the source does not actually support — this defect is invisible in Recall@k (the retrieval still "succeeds") and only visible on direct inspection;
4. re-run this audit whenever you change the generation prompt or the underlying LLM — a prompt or model change can silently shift how often unsupported questions are generated.

## Common traps

- trusting Recall@k as sufficient validation for a QA-pair pipeline — a misleading synthetic question that promises an answer the source doesn't contain still "succeeds" on that metric while corrupting the resulting retrieval;
- generating questions with too little variation in specificity or phrasing, so the artifact set covers only a narrow slice of how real users actually ask;
- letting the QA pair's generated *answer* leak into generation instead of routing strictly to the source chunk — this breaks the core pattern from the next page and reintroduces the citation risk derivative artifacts are meant to avoid;
- skipping manual spot-checks because the pipeline "looks like it's working" in aggregate metrics — the specific failure mode here is designed to be invisible in aggregate and obvious on direct read.

## Takeaways

- QA pairs work by making the indexed object same-genre with the query (question against question), removing a genre gap that plagues raw declarative-prose retrieval.
- This fix is orthogonal to accuracy — a well-phrased, well-matched question can still point to a chunk that doesn't actually support the implied answer.
- Concretely: manually audit a sample of generated QA pairs against their source chunks before trusting the pipeline at scale — Recall@k cannot catch a misleading synthetic question, only direct inspection can.
